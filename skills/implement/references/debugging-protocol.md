# Debugging Protocol

implement 阶段修复 bug 时的根因分析流程。

## 4 阶段流程

修复任何 bug 前，必须依次完成以下 4 个阶段：

### 阶段 1：调查（Investigate）

- 确认现象：bug 的具体表现是什么？
- 确认复现路径：如何稳定复现？
- 收集证据：错误日志、堆栈信息、截图、用户报告
- **禁止在调查完成前提出修复方案**

### 阶段 2：模式分析（Pattern Analysis）

- 在代码中定位可疑区域
- 分析调用链和数据流
- 列出可能的根因假设（不超过 3 个）
- 按概率排序假设

### 阶段 3：单假设测试（Hypothesis Testing）

- 每次只测试一个假设
- 写一个能验证/推翻该假设的测试或实验
- 运行测试并记录结果
- 如果假设被推翻，回到阶段 2 测试下一个假设

### 阶段 4：实施修复（Fix）

- 只在根因确认后才开始修改代码
- 修改范围限制在根因涉及的最小区域
- 写回归测试防止 bug 复现
- 运行完整测试套件确认无副作用

## 失败保护机制

- **连续 3 次修复失败**（修了还有问题、测试还是不过）→ 必须停止
- 停止后向用户报告：
  - 已尝试的修复方案及结果
  - 当前对根因的理解
  - 建议的下一步（可能需要讨论架构问题）
- **禁止**第 4 次盲目尝试

## 与反馈处理的结合

当收到 review 或 test 反馈指出 bug 时：

1. **先验证问题是否成立**：可能 reviewer 误读了代码，或 test 环境有差异
2. 问题确认成立后，进入 4 阶段流程
3. 对不明确的 feedback，追问而非盲目实施
4. 保留技术性怀疑能力，不做表演式认同

## 常见反模式

| 反模式 | 正确做法 |
|--------|----------|
| 看到报错立即改代码 | 先走完调查和模式分析 |
| 同时修改多处 | 每次只测试一个假设 |
| "感觉应该是这里" | 用证据和测试验证假设 |
| 反复试不同的修复 | 3 次失败后停止，向用户报告 |
| reviewer 说什么就改什么 | 先验证 feedback 是否成立 |
