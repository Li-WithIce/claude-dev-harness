# TDD Protocol

implement 阶段的测试驱动开发铁律。

## RED-GREEN-REFACTOR 循环

每个 TODO 实现时必须遵循以下循环：

### 1. RED（写失败测试）

- 在实现任何业务代码之前，先写一个会失败的测试
- 测试描述应当反映 TODO 的验收标准
- 运行测试，确认测试**确实失败**
- 如果测试意外通过，说明 TODO 的验收标准可能已经被满足，或测试写错了

### 2. GREEN（写最小实现）

- 编写刚好能让测试通过的最小实现
- 不要提前优化，不要写额外功能
- 运行测试，确认测试**通过**

### 3. REFACTOR（重构）

- 测试通过后，检查是否有重复代码、命名不清晰、结构不合理的地方
- 重构时保持测试持续通过
- 重构完成后再次运行全部相关测试

## 何时可以跳过 TDD

只有在以下情况下可以不先写测试：

1. **用户显式许可**：用户明确说"不需要先写测试"或"跳过 TDD"
2. **纯配置/文档变更**：不涉及可执行代码的修改（如 Markdown、配置文件、环境变量）
3. **测试基础设施不存在**：项目完全没有测试框架，且当前 TODO 不包含搭建测试框架

如果跳过 TDD，必须说明原因和替代验证方式。

## TDD 与 TODO 的关系

- 每个 TODO 的验收标准 = 测试的断言条件
- Plan 中的验证命令 = 测试运行命令
- 测试文件路径应遵循 Plan 中的指定路径，或项目既有的测试命名约定

## 常见反模式

| 反模式 | 正确做法 |
|--------|----------|
| 先写完所有代码再补测试 | 每个 TODO 先 RED 再 GREEN |
| 测试只验证"不报错" | 测试验证 TODO 的验收标准 |
| 重构时不跑测试 | 每次重构后立即运行测试 |
| GREEN 阶段写大量额外代码 | 只写让测试通过的最小实现 |
| 跳过 RED 确认（不看测试失败） | 必须确认测试先失败再写实现 |
