# Requirement Gate

Requirement Gate 在任何写入前回答一个问题：当前证据是否足以确定“要实现什么”，还是仍有必须由用户或更高权威来源决定的事项。

## 它读取什么

权威顺序是：

1. 当前用户指令与本轮确认；
2. 用户明确引用并批准的来源；
3. 项目产品决定；
4. 项目架构决定；
5. 当前代码、公共接口与测试；
6. 工程约定。

低层来源只能补充自己有权决定的内容，不能覆盖高层来源。同级批准来源冲突时保持阻断；新需求与旧测试冲突时，以已确认的新需求为准。

## 何时进入 Ask

只有未决答案会改变产品行为、权限、金额、数据保留/删除、公共兼容、不可逆架构或生产结果时，Requirement 才是 blocked，并进入 Ask。Ask 期间不改代码、不创建任务状态，也不把“获取 Approval 或补 Evidence”误判为需求澄清。

对于已接入项目连续记录的改造请求，可以先在项目既有变更说明位置保存一份标记为“待澄清”的草稿，只记录用户原话、已知来源及日期和待确认问题，不补造答案或原因。草稿不改变 blocked 状态，也不授权代码、机器任务状态、runtime、受保护操作或数据库写入；只读请求仍零写入。受保护或超出范围的工作仍须在写入前按现行策略分流。

代码、文档和测试可以回答的问题先自行查证。普通命名、私有 helper、文件拆分、测试组织等可逆且不改变产品语义的工程细节由 agent 决定。

## 何时可以退出

退出 Ask 前必须能够明确说明：

- 用户目标与成功/验收标准；
- in scope 与 out of scope；
- 影响区域与约束；
- 风险和预期输出；
- 推荐的 Direct 或 Governed/Critical 路径，以及为什么安全。

Requirement clear 只表示产品意图足够明确，不代表已取得受保护动作的 Approval，也不代表验证已经完成。后续风险策略仍可要求计划、回滚、dry-run、独立审查或 Evidence。

明确接入项目连续记录的项目，在需求 clear 后、代码改动前把要求、原因和验收写入业务变更说明；若已有待澄清草稿，保留原话并补充用户确认的答案。普通 Markdown 交付不等同于策略中的机器任务持久化，不因维护文档设置 `Persistence=durable` 或 `DurableArtifactsRequested`。

机器契约的字段、枚举与校验规则以 `schemas/`、`policies/` 和实现模块为准，本页不复制它们。
