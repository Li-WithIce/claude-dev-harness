## 1. 要解决的问题与完成标准

目标是完善 Harness 的通用开发工作流：换对话后仍能使用已经验证的操作方式和配置；新需求能查到提出原因、实现过程、验证结果和对应代码版本。工作台用于验证这些能力，通用规则和模板不写死其路径、技术栈或发布命令。

最终用以下真实场景验收，不能只用“文件已生成”或“工具已安装”代替：

1. 新开工作台对话，只说“按上次的方式打生产包”，代理找到相同的已验证入口和配置来源，不要求用户重新解释，不自行改用另一套打包方法。
2. 新需求先保存要求、原因和验收标准；实现一部分后切换对话，能够恢复已完成内容、未完成内容和验证状态。
3. 上下文压缩后，继续操作前重新读取相关记录，仍使用相同的脚本和有效配置。
4. 用户问“这个功能为什么这样改”，能给出原始要求、变更记录和前后端对应提交，区分后续替代方案。
5. 未打包、未测试、未发布的部分明确标注，搜索结果和模型摘要不能将它们改成已完成。

## 3. 最小方案与记录位置

采用“当前项目约定 + 每次改造记录 + 已验证操作入口 + 按需历史检索”。记录由当前执行工作的代理在关键步骤维护；用户不需要重复填写表格。

Harness 要提供的五项通用能力：

| 能力 | 最小实现 | 验收重点 |
| --- | --- | --- |
| 需求留痕 | 开发前在项目变更记录中写明要求、原因和验收 | 用户要求与代理判断分开，后续变化保留原因 |
| 过程接续 | 关键步骤后更新已完成、未完成及验证结果 | 新会话和压缩后能找到最后一次落盘进展 |
| 操作复用 | 项目说明链接已验证脚本与配置来源 | 执行前读取原入口；确需改变时说明依据并更新记录 |
| 结果溯源 | 记录分别关联实现提交、测试、包及实际发布 | 能从原因追到代码，也能从代码追到原始要求 |
| 内置检索 | 固定入口直接读；背景历史使用现有 `context.ps1 recall/read` | 原文可回读，旧方案不覆盖当前约定，缺失信息不臆造 |

本轮不新增向量数据库、后台摘要服务、语义检索适配或第三方记忆依赖。将来只有本地检索出现可证实的不足时，再单独评估改进。模板和规则只是实现材料，真实接续和复用行为通过后才算完成。

### 3.1 工作台的唯一文档归档位置

首版建议把跨前后端的项目文档放在已有后端仓库，复用 Git，不新建第三个仓库：

| 计划路径 | 内容与维护方式 |
| --- | --- |
| `D:\working\workbench-service\docs\project-context.md` | 项目目标、前后端位置、现行约定、操作文档位置、尚未结束的改造链接；保持简短，不堆对话日志 |
| `D:\working\workbench-service\docs\operations\build-release.md` | 已验证打包入口、工作目录、工具版本、配置加载方式、产物位置；构建和部署分开说明 |
| `D:\working\workbench-service\docs\changes\<日期>-<主题>.md` | 一次有独立目的的改造一份记录；前后端共同改动也只维护这一份 |
| `D:\working\PROJECT.md` | 用户维护的接入标记和共享文档导航；Harness 安装更新保留 |
| `D:\working\AGENTS.md` | Harness 生成的总入口，规定读取已接入的 PROJECT，避免把业务路径写入生成文件 |
| 两个实际仓库各自的 `PROJECT.md` 和 `AGENTS.md` | 简短导航到同一份共享文档，支持从前端或后端目录启动对话；不复制正文或进度 |

上述文档位置是本计划的设计选择，不表示文件已经存在。前端改动记录落到后端文档目录的取舍是会产生跨仓库文档变更；换来的好处是一份产品级记录能够同时关联两个提交。若已有合适的团队文档仓库，实施前可以改为该仓库，不能把 `D:\working\docs` 误当成已受 Git 管理。

文档在批准的提交流程中入库；不为留下记录擅自提交或推送业务代码。未提交期间标记“本地未提交”，能跨窗口读取，但不能声称已经有远端版本保障。

### 3.2 一份改造记录包含什么

```markdown
# <日期与改造主题>

## 改造前
- 原始要求：保留用户表达中的关键约束。
- 原因：用户给出的原因；未提供就注明，代理判断另列。
- 当前行为与目标行为：简短 before/after。
- 范围与验收：本次要做到什么、涉及哪些仓库。
- 来源：可用的对话引用、需求文档或工单；没有就注明。

## 过程与进展
- <时间>：重要决定、需求变化及原因。
- 已完成：具体文件或功能。
- 下一步：明确的待办与尚未解决的问题。
- 验证状态：通过、失败或尚未运行。

## 交付与发布
- 前端：仓库、基线提交、实现提交；未提交则据实记录。
- 后端：仓库、基线提交、实现提交；未涉及则注明。
- 验证：命令、工作目录、结果、必要的日志或证据位置。
- 打包：实际脚本与参数、配置来源、产物位置和摘要。
- 发布：目标、实际版本、时间；仅打包则写“未发布”。
- 关联：前序改造、后续修正、替代或回退记录。
```

小改动使用同样信息的短版本，不要求填满长表。只读问答不建变更记录；同一需求中的多次编辑不拆成多份。需求变化追加说明，不覆盖最初的理由。历史补录标注“补录日期、原始来源、未核实内容”，不能伪造当时已记录。

代码提交无法引用包含自身的最终哈希：先在代码提交消息中引用变更记录标识；提交完成后再回填实现提交号，文档随后提交即可。前后端分别记录，不能只记父目录或一个仓库的 HEAD。

当前有效配置中的敏感值继续保存在项目规定的位置。记录配置路径、变量名、加载顺序和适用环境，不把凭证复制到日志、历史摘要或检索索引。

## 4. 对话开始、进行与结束时的具体行为

1. **开始开发**：读项目入口和简短项目说明；涉及打包就直接读操作文档，涉及已有功能就读相关改造记录。关键入口用确定路径读取，不依赖搜索排名。
2. **改动代码前**：写明已明确的要求、原因、范围和验收。可由代码和文档查证的问题先查证；确实影响业务含义的不确定项再询问。
3. **关键步骤后**：在完成一块实现、验证结束、需求改变或准备交接时更新同一份记录。不每次工具调用都写日志，不创建额外辅助状态系统。
4. **结束本轮前**：写入实际结果与下一步；成功流程被采用后更新现行操作说明。确认文件已写入后，才在答复中说“已记录”。
5. **新会话或压缩后继续**：从当前项目说明找到候选记录，读取其要求、进展和现行操作入口；核对工作树再继续。多条并行需求按当前用户目标匹配，不能把“最后修改的一条”默认当成当前任务。
6. **约定被替代**：更新现行文档并链接变更原因，旧记录保留。`superseded_by` 只用于明确被替代的规范文档；历史事件本身不会因为较旧而失效。

跨会话可恢复的承诺以“最后一次已落盘的步骤”为界。窗口被强制关闭、进程崩溃前尚未写入的内容，不承诺零丢失；恢复时报告最后记录时间并对照当前 diff。重要参数要写入脚本、配置或操作文档，不能只保存在终端临时环境里。

工作台总目录及前后端子目录启动的对话，需要显式映射到同一个工作台文档入口。原始会话检索仍保持现有精确 cwd 规则，首版不把它放宽成搜索所有项目，也不把其他 worktree 的进行中状态自动合并进来。

## 5. 实施顺序、交付物与阶段验收

### P0：核实通用流程缺口与工作台成功基线

工作：

- 对照“要求 → 改造 → 验证 → 打包/发布 → 后续修正”，列出当前 Harness 缺失的记录及读取触发点，确定哪些沿用 Direct，哪些复用既有 v2 Governed。
- 检查最近一次成功打包的对话、脚本、构建日志和产物；优先精确查用户指出的“打生产包”对话，不遍历全部历史。
- 确认前后端真实命令、cwd、工具版本、依赖安装方式、构建 profile、环境变量、配置加载顺序、包结构及发布目标。
- 区分临时 `.build` 副本和实际仓库中的可维护入口；已有脚本适用就保留，仅在实际缺少稳定入口时固化必要步骤。
- 保留 `.env.production` 现有修改，先记录是否参与当前构建，不擅自恢复、覆盖或把它归入自己的改动。
- 只补录“项目现状、最近成功打包、当前关键配置”三类基线。旧需求文档按需引用，不一次性迁移全部历史。

交付：上述项目说明、操作说明和一条标明来源的基线记录草稿；需要确认的业务差异单列。

验收：每个关键命令和配置来源都有依据；未证实的版本或步骤写 `NOT_VERIFIED`，不能凭 README 或文件时间猜测成功流程。P0 不执行生产部署或数据库写入。

### P1：实现 Harness 最小连续工作规则

工作：

- 增加可复用的简短项目说明、变更记录、操作说明模板和使用指南；不新增生命周期 CLI、守护进程或数据库。
- 明确新任务、继续任务、打包、历史追问四类读取触发点；关键约定直接读固定文件，历史背景复用现有 `context.ps1 recall/read`。普通小改动仅加载本次相关资料，不全量扫描所有对话。
- 明确写入触发点：代码改动前、需求变更时、关键实现或验证结束后、本轮交接前。完成后回读必要记录，避免只在最终答复中口头声称已经保存。
- 调整入口契约：允许已接入项目在普通 Direct 中维护轻量业务文档；仍不创建 v2 task state、current pointer 或机器 Evidence。只读工作继续零写入。
- 将“持久业务说明”与“要求机器状态和正式 Evidence 的 Governed”分清；不能因加一份变更说明就把普通改动全部升级成 Governed。
- 对已有 Governed/Critical 任务，变更说明链接其 canonical task/Evidence；机器任务状态仍以现有 v2 runtime 为准，不维护第二份可驱动执行的状态。
- 新行为通过项目明确接入生效。此次先接入 working，不自动改变 GVPP、energy 等其他项目，也不覆写用户级开发准则。
- 复用 `generate-entry-contract.ps1` 更新生成入口；安装器不得覆盖用户维护的项目说明和历史记录。

这是对当前 Direct“零任务产物、无自动记录”说明的有限调整，必须同步规则、指南与相关测试，不能靠新文档暗中覆盖旧契约。是否需要修改实际 profile 解析，由其现有输入判断：业务记录不能被误传为要求正式 Evidence 的 `durable` 条件；发现这种耦合时只改该映射并补行为测试。

交付：通用模板与规则、小范围行为检查、生成契约和安装更新验证记录。

验收：接入项目的新改造能够维护业务记录；普通 Direct 仍无 runtime/current/Evidence 副作用；未接入项目维持原有行为；Hook 关闭偏好和用户规则保持原值。

### P2：工作台接入与固定打包方式

工作：

- 在确认 P0 基线后维护可入 Git 的项目文档，更新 working 当前入口；移除入口对退役 v1 执行链的依赖，保留旧资料作为历史来源。
- 现有前后端打包入口能复用就直接复用。若成功命令只存在于旧对话，按原方式固化到相应仓库的最小脚本中，避免新增一套构建逻辑。
- 前后端脚本使用各自现有工具链；需要双仓库联合打包时，仅用一个薄入口调用它们，且只在确有重复联合操作时增加。
- 操作文档写清非敏感参数、配置引用、产物规则、执行环境和验证方式；不依赖上一窗口临时设置的变量。
- 做一次授权范围内的本地构建复测。构建成功和业务测试通过分别记录；测试被跳过时明确说明，不能把 Maven `BUILD SUCCESS` 当作测试通过。

交付：工作台可复用操作入口、现行文档、第一条完整基线记录。

验收：从新终端按文档执行，参数和配置来源一致，生成预期包结构；记录两个仓库的实际修订和 dirty 状态。不同构建产生的包不要求字节完全相同，不把时间戳差异误判为流程改变。是否已经部署单独报告。

### P3：真实跨会话与新需求试点

工作：

- 使用用户后续真实的新需求，先记录要求和原因，再实现、验证、关联提交，最后更新现行说明。
- 在至少一个已落盘的中间步骤切换到 working 新对话，验证它能恢复下一步，而不是重新猜一套方案。
- 单独验证“按上次方式打包”和一次上下文压缩后的继续操作。
- 检查同一产品两个仓库和不同启动目录是否都能定位到同一份记录。

交付：一条真实需求的完整记录、跨会话观察与缺口清单。

验收：通过第 7 节的业务场景。新会话和真实压缩测试需要实际宿主行为；脚本 fixture 不等价。如当前无法触发或观察压缩，则标 `not_run` 或 `unavailable`，对应验收保持未完成。不会为凑证据创建无意义的业务改动。

### P4：固化通用能力并逐项目推广

工作台至少完成一次真实新需求闭环和一次跨窗口重复打包后，总结必要规则，再对用户指定的其他项目逐个接入。不批量改写全部工作区、不批量导入旧对话。

每个项目沿用“项目文档 + 现有脚本 + 按需检索”，不复制工作台的业务参数和路径。推广时分别验证该项目入口与 Git 归档位置。

交付：Harness 通用入口、模板、使用指南与正常安装更新路径；工作台作为完整验收样例。

验收：通用资产不含 working 特定路径或业务参数；用最小的独立夹具验证另一种项目布局也能定位文档、维护记录和回读历史。夹具验证只证明可移植性，不替代工作台的真实使用验收。

## 7. 验收清单

| 编号 | 场景 | 通过条件 |
| --- | --- | --- |
| AC-1 | 改造前留痕 | 代码修改前已保存原始要求、原因/未提供标记、范围和验收；可读回 |
| AC-2 | 原方式再打包 | 新对话无需补述历史，选中原验证入口和配置来源；差异有依据 |
| AC-3 | 配置接续 | 新终端不靠上一窗口临时状态即可按说明运行；敏感值不进入检索资料 |
| AC-4 | 中途换会话 | 从最后落盘进展恢复，正确说明未完成项，不把旧测试结果算作本次通过 |
| AC-5 | 压缩后继续 | 真实压缩后重新读取相关记录并继续；模拟验证不能代替 |
| AC-6 | 原因与代码溯源 | 一条问题能定位用户要求、改造记录、前后端实现提交及验证；未提交如实标明 |
| AC-7 | 后续需求覆盖旧约定 | 新要求成为现行约定，原始原因和旧方案仍能追溯 |
| AC-8 | 并行与多目录 | working 总目录/前端/后端能定位同一产品文档；多个进行中改造不相互覆盖 |
| AC-9 | 最小依赖 | 完整工作流使用项目文件、Git 和 Harness 现有本地能力完成；不依赖外部记忆产品、云服务或 Hook；Direct 无机器任务状态写入 |
| AC-10 | 现有资产保留 | 原暂存文件、工作台 `.env.production` 用户修改及 Hook 关闭偏好保留；无数据库权限扩大 |
| AC-11 | 内置查询与可移植性 | “上次怎么打包”“为什么改”“配置在哪”“做到哪一步”“旧方案何时被替代”能回到对应原文；通用资产无工作台硬编码，另一项目布局夹具通过 |

验证顺序：聚焦行为检查 → 受影响入口/分发检查 → 仓库要求的相应验证组 → 工作台本地复测 → 真实新会话与压缩试点。相同 checkout 中会修改共享夹具的测试顺序执行，不并行制造假失败。保留原失败退出码及修复后的证据。

## 8. 实施边界、回退与待核实项

- 用户已授权按本计划实施；每项实际结果与未完成验收在本轮执行记录更新，不能将计划中的目标当作已完成。
- 实施从 P0 开始。工作台最近成功包对应哪次对话/产物、发布目标与当前工具版本，由现场证据确认；真正需要用户决定的差异再集中说明。
- 原始对话与历史 v1 文档只作背景证据；不继续执行旧生命周期，不批量迁移旧 runtime。
- 撤销入口试点规则即可停止新的自动记录，已经写出的项目历史和操作脚本继续保留，不因回退流程改造而删除。
- 若本次固化的脚本复测失败，保留失败记录，修复必要步骤或恢复既有可用入口；不清理用户文件、不 reset/stash/clean。
- 自动采集整段对话、自动生成 skill、团队共享索引、Obsidian 面板不是首版交付项；后续出现实际需要再单独安排。
