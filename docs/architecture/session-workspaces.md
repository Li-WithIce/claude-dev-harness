# Session workspace grants

The host Hook supplies the documented `session_id` and `cwd`. It does not supply an authoritative list of additional workspace roots. Harness therefore requires an explicit registration for each host session; it never infers authorization from a parent directory, transcript, user prompt, tool arguments, or environment variable.

`scripts/register-session-workspaces.ps1` registers an exact, nonoverlapping set of installed v2 workspace roots. Its inputs are `WorkspaceRoot`, `SessionId`, a JSON string array `AdditionalWorkspaceRootsJson`, `TaskWorkspaceRoot`, `TaskId`, `ExpectedVersion` and `ExpectedCurrentDigest` (`missing` or a SHA256 digest). `DryRun` checks the same bindings and writes nothing. An empty array revokes the additional roots through the same CAS API. The registration requires a running/verifying Critical task with a clear Contract and a current architecture Approval whose protected operation covers the exact session, root paths and physical identities, and expected registry preimage. Approval identity is constructed with the existing `New-HarnessProtectedOperation`: target is the hashed session registry path; scopes are `rule:session-workspace-registration`, `path:<registry path>` and the SHA256 command digest of the compact ordered intent `{session_id, primary, workspaces, expected_current_digest}`. Each workspace descriptor is ordered `{path, identity}`. The task's version and Contract digest remain part of that protected operation's identity.

Registration uses the existing physical-identity mutex, strict JSON schema and atomic CAS writer, then records Approval provenance and expiry under `.assistant/runtime/session-workspaces/<sha256-of-session-id>.json`. It does not activate current pointers, import old Approval, or consume target business Approvals. Ordinary file mutations and the controlled-write adapter cannot edit this control path. This registry is maintained by the trusted installation/operator workflow; the existing Hook is a guardrail, not an operating-system sandbox. A hostile same-account shell can replace control files, so OS account/ACL isolation remains the boundary for adversarial writers.

The adapter resolves every relative path against host cwd. Only an absolute outside target may use a registered root; no session or an unregistered target retains the original path denial. The ordinary cwd-contained path does not read a registry or require a session ID. Extra roots are revalidated for installed v2 admission, physical identity and expiry, and each resolved target still passes the existing containment and reparse checks. A SUBST/volume-GUID alias of a registered root is not an additional grant; use the registered absolute path spelling. Alias roots with the same physical identity cannot be registered twice.

All patch and move targets are grouped by their workspace. Each group is checked against that workspace's protected overlay, task, Contract and Approval, using the supplied task id/version only within that workspace. Any failure refuses the entire preflight; the adapter writes no files and consumes no Approval. For cross-workspace requests, `workspace_checks` preserves the individual authorization results. Aggregate Approval/operation fields are null because one workspace's Approval cannot represent all groups. The four Adapter API operations remain unchanged; `session_id` and `workspace_checks` are additive optional fields.

The grants cover file tools and direct patches. Shell commands retain their existing cwd-based policy path because the Hook contract does not expose a reliable normalized shell target list. Do not interpret a successful fixture or installed configuration as observed desktop execution. `tests/verify-session-workspaces.ps1` verifies registration, scoped routing and rendered Hook transport in isolated Temp directories; real session IDs and business files require separate host evidence.
