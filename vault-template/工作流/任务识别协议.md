# 任务识别协议

## 目标

在“继续当前任务 / 切换已有任务 / 创建新任务 / 先入收件箱”之间做轻量且可复用的判定，避免多任务切换时共享指针和中断清单漂移。判定为 `new-task` 后，再用一层轻量模式路由选择 `quick | workflow | ask`，避免把所有新事项默认升级成完整 workflow。

## 判定顺序

1. **显式任务标识优先**
   - 用户明确给出 `task_id`
   - 用户明确说“继续 / 恢复 / 切换到 …”
   - 用户明确给出某个 artifact 路径
2. **工作区与 artifact 命中**
   - 当前 cwd 与 `运行时/tasks/<task-id>.md` 的 `workspace` 匹配
   - 或命中 `primary_artifact` / `artifact_links`
3. **共享指针优先**
   - 若请求与 `当前任务.md` 的 `task_id`、工作区和下一步一致，判定为继续当前任务
4. **中断任务候选**
   - 若请求更接近 `中断任务.md` 中某个任务，判定为切换
5. **仍不确定**
   - 先写 `收件箱.md`
   - 由入口 agent 再升级为新任务或中断任务

## 输出类型

- `resume-current`：继续当前主任务
- `switch-existing`：切换到已有中断任务
- `new-task`：创建新任务
- `inbox-first`：信息不足，先入收件箱

## new-task 模式路由

`new-task` 只说明“不是当前任务或已有中断任务”，不等于自动进入完整 harness-lite workflow。入口 agent 先根据用户意图和风险选择 `mode`：

- `quick`：低风险、边界清楚、可在当前对话内直接完成和验证的小改动 / 简短回答。默认不创建 `docs/tasks/<task-id>/`，不改共享指针。
- `workflow`：需要计划、留痕、review、test、多文件/跨模块协作、较高风险或用户明确要求可审计产物时，进入 orchestrator 创建 `docs/tasks/<task-id>/plan.md`。
- `ask`：只有路由置信度低、显式信号冲突或缺少判断 quick/workflow 的关键信息时使用；只问一个最小澄清问题。

### 显式覆盖关键词

- 偏 `quick`：用户说“直接改”“快修”“小改一下”“不用 workflow”“别走流程”等。
- 偏 `workflow`：用户说“走 workflow”“留痕”“需要 review”“需要 test”“跑完整流程”“写计划”等。
- 若同一请求同时出现 quick 与 workflow 信号，以更高风险或更明确的审计要求为准；仍无法判断才 `ask`。

### Clarification 协议触发词

当开发任务中出现“需求澄清”“需求确认”“拷问需求”“拷问方案”“方案压力测试”“头脑风暴”“设计访谈”“边界确认”“验收标准确认”“非目标确认”，或 `clarify` / `brainstorm` / `pressure test` / `challenge this plan` / `ask me questions` / `interrogate the requirement` 等同族表达时，进入 Clarification 协议。

- 需要可审计决策、后续实现或跨阶段留痕时，判定为 `workflow`，在 `PLAN -> ## Clarification` 中记录问题、推荐答案、决策和边界；用户确认前 `## User Confirmation` 保持 `draft`。
- 只有任务归属、目标或风险边界不足以判断 quick/workflow 时才判定为 `ask`，并且只问一个最小澄清问题。
- 能通过代码库、文档或 artifact 回答的问题，入口 agent 先自行查证，再给出推荐答案。
- 该协议不是新 stage，不新增 runtime、frontmatter 字段、validator hard gate 或第二 truth。

### 默认判断

- 优先自主判断，不把 `ask` 当默认入口。
- 窄范围、单文件或文档小修、验收清楚、失败影响低、可立即验证时，默认 `quick`。
- 需求仍在形成、影响面不清、需要用户确认验收、会改共享协议 / 脚本 / 多阶段产物、或需要独立 review/test 证据时，默认 `workflow`。
- `quick` 执行中若发现影响面扩大或需要留痕，立即停止扩大实现并切换为 `workflow` 或向用户确认。

## 自动懒加载规则

完成输出类型判定与 `new-task` 模式路由后，再按模式加载后续材料：

- `quick`：只加载入口规则、用户偏好 / 必要配置，以及与本次请求直接相关的 skill 或 reference。
- `workflow`：加载 `entry-router`、`orchestrator`，再按当前 stage 加载一个阶段 skill：`PLAN -> plan`、`PLAN_REVIEW -> review`、`IMPLEMENT -> implement`、`CODE_REVIEW -> review`、`TEST -> test`。
- `resume-current` / `switch-existing`：只加载 `恢复索引.md`、`当前任务.md`、`运行时/tasks/<task-id>.md`；必要时只读当前任务 `plan.md` frontmatter 判定 stage，再加载当前 stage skill。
- `ask`：不加载 workflow skill，只问一个最小澄清问题。

禁止 bulk-load 全部 skills、全部历史任务、Claude 兼容 skill、`workflow-team`。只有显式 backend override、当前 stage/frontmatter 命中、或 team-mode env 触发时才加载这些路径。

## 写回规则

- 从一个未完成任务切到另一个任务前，先把旧任务写入 `运行时/tasks/<task-id>.md`
- 若旧任务尚未完成，再由入口 agent 写入 `中断任务.md`
- 最后才允许切换 `当前任务.md`

## 派生规则

- `当前任务.md` 是当前激活任务的共享指针真相源
- `中断任务.md` 与 `恢复索引.md` 是派生视图，不能比共享指针更权威
- 恢复选项必须基于共享指针 + 任务状态文件重新生成，不手工维护独立文案

## 单写者判定

- `entry_host` 决定本次共享写入是否合法
- 缺失 `entry_host` 的旧文件按 `task-runtime/v1.0-legacy` 回退到 latest writer 推断
- `entry_host` 描述 agent 平台；`entry_tool` 描述 backend，二者不可混淆

## 任务状态文件最低匹配键

- `task_id`
- `task_name`
- `workspace`
- `primary_artifact`
- `artifact_links`
- `entry_host`
- 最近阶段 / 下一步
