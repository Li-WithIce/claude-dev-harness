# 任务识别协议

## 目标

在“继续当前任务 / 切换已有任务 / 创建新任务 / 先入收件箱”之间做轻量且可复用的判定，避免多任务切换时共享指针和中断清单漂移。判定为 `new-task` 后，再用一层轻量模式路由选择 `quick | workflow | ask`，避免把所有新事项默认升级成完整 workflow。

## 判定顺序

0. **未完成写回优先**
   - 可只读检查 `运行时/收件箱.md` 中 open `[writeback-fallback]`
   - 只有用户明确继续 / 切换并执行目标 workflow 时，才按实际 stage 重放 `-SyncOnly`；read-only inspect/status 不 replay、不 sync
1. **显式任务标识优先**
   - 用户明确给出 `task_id`
   - 用户明确说“继续 / 恢复 / 切换到 …”
   - 用户明确给出某个 artifact 路径
2. **工作区与 artifact 命中**
   - 当前 cwd 与 `运行时/tasks/<task-id>.md` 的 `workspace` 匹配
   - 或命中 `primary_artifact` / `artifact_links`
3. **共享指针优先**
   - 若请求与 `当前任务.md` 的 `task_id`、工作区和下一步一致，判定为继续当前任务
4. **中断任务候选**
   - 若请求更接近 `中断任务.md` 中某个任务，判定为切换
5. **仍不确定**
   - 交互式归属或读写歧义先 `ask`，不写 `收件箱.md`
   - 只有已授权持久捕获的 actionable/durable 外部事项才 `inbox-first`，再由入口 agent 分诊

## 输出类型

- `resume-current`：关联当前主任务；只有明确继续执行才恢复/写回
- `switch-existing`：关联已有中断任务；只有明确切换并执行才激活/写回
- `new-task`：创建新任务
- `inbox-first`：已授权持久捕获但暂缺 task identity 的 actionable/durable item

## new-task 模式路由

`new-task` 只说明“不是当前任务或已有中断任务”，不等于自动进入完整 harness-lite workflow。完整 precedence 以 `entry-router` 为准；本协议只保留边界：

- project-scoped standalone pure read-only 且目标、范围、输出清楚时走 `quick`，不创建 `docs/tasks/{task_id}/`、不改共享指针；代码区域高风险只提高证据强度，不自动授权 artifact。
- mixed mutation 不使用 read-only shortcut：低风险、窄范围、可立即验证时仍可 quick；跨模块、高风险或明确要求 durable workflow/review/test evidence 时走 `workflow`。
- 读写意图、任务归属或阻塞要求仍不清楚时走 `ask`。Ask mode is an iterative blocking clarification gate；默认一次问一个最高价值问题，用户回答后重新判断，Remain in ask until all blocking uncertainties are resolved。
- active task 先按 resume/switch 归属，但 route identity does not broaden requested action；真正非项目请求仍交宿主。

### Clarification 协议触发词

当开发任务中出现“需求澄清”“需求确认”“拷问需求”“拷问方案”“方案压力测试”“头脑风暴”“设计访谈”“边界确认”“验收标准确认”“非目标确认”，或 `clarify` / `brainstorm` / `pressure test` / `challenge this plan` / `ask me questions` / `interrogate the requirement` 等同族表达时，进入 Clarification 协议。

- 需要可审计决策、后续实现或跨阶段留痕时，判定为 `workflow`，在 `PLAN -> ## Clarification` 的 `clarification_ledger` 中记录 `category / question / evidence / recommended_answer / decision / impact`，并保留 Clarification 最低字段；用户确认前 `## User Confirmation` 保持 `draft`，存在 `decision: pending` 时不得确认。
- 只有任务归属、目标或风险边界不足以判断 quick/workflow 时才判定为 `ask`；简单歧义可能一个问题就解决，但 ask 仍保持阻塞，直到所有会影响路由或实现的问题都清楚。
- 触发范围也包括 PLAN 的验收、非目标、影响面、回滚/兼容仍不确定，或实现路径仍不足以指导 IMPLEMENT；能通过代码库、文档或 artifact 回答的问题，入口 agent 先自行查证，剩余用户决策按依赖顺序一次只问一个并给出推荐答案。
- 该协议不是新 stage，不新增 runtime、frontmatter 字段、validator hard gate 或第二 truth。
- 阶段原则路由也只是认知视角，不新增五转流程：Entry/Clarification 用 Socrates，PLAN 用 Osborn/Hegel/First Principles/Occam，PLAN_REVIEW 用 Hegel+Bayes，IMPLEMENT 用 Ponytail/surgical change，CODE_REVIEW 用 Feynman，TEST 用 Bayes，revise 后用 Debono 保留仍成立的价值和约束。

### 默认判断

- 优先自主判断，不把 `ask` 当默认入口。
- 窄范围、单文件或文档小修、验收清楚、失败影响低、可立即验证时，默认 `quick`。
- 需求仍在形成或读写边界不清时走 ask；mutation 会改共享协议 / 脚本 / 多阶段产物，或需要 durable independent review/test evidence 时走 workflow。
- `quick` mutation 若影响面扩大，或用户新增 durable artifact 要求，立即停止扩大实现并切换 workflow 或确认；read-only review/test 名词本身不触发切换。

## 自动懒加载规则

完成输出类型判定与 `new-task` 模式路由后，再按模式加载后续材料：

- `quick`：只加载入口规则、用户偏好 / 必要配置，以及与本次请求直接相关的 skill 或 reference。
- `workflow`：加载 `entry-router`、`orchestrator`，再按当前 stage 加载一个阶段 skill：`PLAN -> plan`、`PLAN_REVIEW -> review`、`IMPLEMENT -> implement`、`CODE_REVIEW -> review`、`TEST -> test`。
- `resume-current` / `switch-existing`：先只读 identity/runtime/artifact；只有明确继续 / 切换并执行时才处理 fallback、`-SyncOnly` 收敛/激活并加载 current stage skill。read-only inspect/status 保持零写且不加载 stage skill。
- `ask`：不加载 workflow skill，不创建 `docs/tasks/{task_id}/`，不改代码，不进入 quick、workflow、PLAN、IMPLEMENT 或后续阶段；默认每轮只问一个最高价值问题，阻塞到足以判断路由和验收边界。

## ask 退出标准

ask cannot exit until the agent can state:

1. User goal:
2. Success / acceptance criteria:
3. In scope:
4. Out of scope / non-goals:
5. Affected area:
6. Constraints:
7. Risk level:
8. Expected output:
9. Recommended route: quick or workflow
10. Why this route is safe:

If any item is materially unknown and affects the work, remain in ask.

禁止 bulk-load 全部 skills、全部历史任务、Claude 兼容 skill、`workflow-team`。只有显式 backend override、当前 stage/frontmatter 命中、或 team-mode env 触发时才加载这些路径。

## 写回规则（仅明确继续 / 切换并执行的 workflow）

- 从一个未完成任务切到另一个任务前，先把旧任务写入 `运行时/tasks/<task-id>.md`
- 若旧任务尚未完成，再由入口 agent 写入 `中断任务.md`
- 最后读取目标 task 的实际 frontmatter stage，并只通过 `advance-stage.ps1 -ExpectedStage <actual> -SyncOnly -ActivateCurrent` 切换 `当前任务.md`；`DONE` 不可激活
- read-only inspect/status 不适用本节：不 replay fallback、不 sync/activate、不更新 current/mirror/inbox、不加载 stage skill

## 派生规则

- `当前任务.md` 是当前激活任务的共享指针真相源
- `中断任务.md` 与 `恢复索引.md` 是派生视图，不能比共享指针更权威
- 恢复选项必须基于共享指针 + 任务状态文件重新生成，不手工维护独立文案

## 单写者判定

- `entry_host` 决定本次共享写入是否合法
- 缺失 `entry_host` 的旧文件按 `task-runtime/v1.0-legacy` 回退到 latest writer 推断
- `entry_host` 描述 agent 平台；`entry_tool` 描述 backend，二者不可混淆

## 任务状态文件最低匹配键

- `task_id`
- `task_name`
- `workspace`
- `primary_artifact`
- `artifact_links`
- `entry_host`
- 最近阶段 / 下一步
